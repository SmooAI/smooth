CLI: close the five paths where `th` destroyed data or reported success it hadn't earned (th-db25d4)

Five P1s from the read-only smooth-repo audit. Ordered here by how much of a real user's data each one takes.

**`restore_workspace` mass-deleted a live workspace from a stale snapshot.** `snapshot_workspace` returned a bare `Ok(())` when `is_unsafe_to_snapshot` REFUSED, so the caller set `snapshot_taken = true` and logged "snapshotted best-seen workspace" for a snapshot it never took. Run 1 snapshots a 190-entry tree; the tree grows past the 200-entry threshold; run 2 skips the snapshot but reports success; a later regression restores run 1's copy over the live tree. Untracked files do not come back. It now returns `io::Result<bool>` so only a COMPLETE snapshot may advance `snapshot_taken`/`best_failed_count`, a mid-copy failure removes the partial tree it left behind, and `restore_workspace` refuses an empty snapshot outright — restoring nothing over a live tree is pure deletion.

**Every delete/revoke verb hit production with no confirmation.** The DELETE fired on the first keystroke, against `https://api.smoo.ai`, using whichever org id was *persisted* as active — written by an `orgs switch` that could have been hours and several contexts ago, and named nowhere on the way to the wire. New `destructive::gate` prints the target (what, which org, which host) on every path including `--yes`, then `--dry-run` stops, non-interactive without `--yes` REFUSES, and a terminal confirms defaulting to no; irreversible targets make you type the target's id back. The audit named nine call sites — a test that walks the whole clap tree found 16 more, including `th config delete` (a config VALUE, with `--env production` one keystroke away), `th api agents delete`, `th api files rmdir` (a whole subtree) and `th api members revoke`. All are wired; local-only verbs are exempt by name in the test, so the next delete verb someone adds either gets the flags or fails CI.

**Commands reported success on failed operations.** `th approve` matched `Ok(_)` from `reqwest::send()` and printed "Approved: <id>" for any status — a 404 from a daemon that had never heard of the bead read as approval, and the command exited 0. `th steer` printed "Error:" and still returned `Ok(())`. `smooth-api-client` did `resp.text().await.unwrap_or_default()`, so a body cut off mid-stream became an empty body, which `decode` reads as the 204-shaped success case and returns `Ok({"ok": true})` — a torn response reported as a completed write. `th jira sync --push` discarded the store write that records the new ticket key with `let _ =`; since `plan_sync` re-derives "is this tracked?" from the pearl TITLE, a dropped write means every later run files ANOTHER production Jira ticket, forever. And `sync_push_pearl_state` funnelled every push error into `tracing::debug!("no remote / offline")` without ever consulting the `is_no_remote_error` predicate defined in the same file, so an expired SSH key meant weeks of pearls existing only on one laptop. Two more instances beyond those the audit named — a 201 CREATED on a discarded comment write in `smooth-diver`'s `post_message`, and a ✓ on a bead migrated with the wrong status — are fixed too.

**`th config push` replaced the whole remote schema with no confirmation.** The push REPLACES the stored key set, so a feature-branch dev with a partial local `schema.json` removes every key it does not declare, in every environment including production. `--dry-run` was opt-in, which made destructive the default, and the "removed" list was computed, printed, and then ignored. Pushes that remove keys or change a tier now confirm and fail closed off a terminal; pure additions stay unprompted. `pick_remote_schema` also stopped guessing: with several remote schemas and nothing to disambiguate it returned `remote_schemas[0]` — an arbitrary pick whose entire key set was then replaced — while `resolve_pull_schema` had refused to guess in that exact situation all along. An existing unit test asserted the guessing behavior; it now asserts the refusal. And `cmd_sync` hard-coded `force = true` into `cmd_pull`, defeating from inside the CLI the one guard standing between a hand-written `schema.json` and a silent overwrite, under a doc comment calling sync "SAFE by design". CI never runs `th config push` — it only verifies the receipt `pnpm config:schema:push` records — so the gate costs automation nothing.

**The sandbox doc claimed confinement it does not have off macOS.** `SandboxedCommand` said "there is no unsandboxed path" and the proxy comment asserted the kernel network-deny "makes this non-optional" — both true only on macOS. Linux and Windows have no FS or network confinement (bubblewrap+Landlock and AppContainer are tracked in th-08e05a; the loud `bash is running UNSANDBOXED` warnings already exist), so the egress allowlist there is advisory: anything that opens its own socket ignores it. smoo-hub runs Linux, so that is the deployed posture. Docs now say so, with a per-platform table and a pointer to `SandboxPolicy::is_enforced` as the runtime answer.
